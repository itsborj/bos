# DEPLOY_TODO.md — Prioritized Task List

> Everything here is ordered by one question: **what does an org need to deploy BOS successfully without Klaroha intervention?**
>
> Internal Klaroha ops tasks (our staging environment, CI config, agent protocol) are at the bottom. They are temporary scaffolding. Building the product correctly makes them irrelevant.
>
> Owner tags: `[claude-code]` = code changes, `[human]` = operator action, `[decision]` = needs human decision first.

## Priority 1 — First-Boot Init (eliminates the entire manual-recovery class)

Every staging incident that required SSH to fix is a first-boot init failure in disguise. This is the single highest-leverage build.

When this exists: `docker compose up` on a fresh server self-configures, self-validates, and bootstraps — no Klaroha intervention, no manual env editing, no format-wrong encryption keys.

| # | Task | Owner | Why it matters |
|---|---|---|---|
| F1-1 | Auto-generate `API_SECRET_KEY` at first boot if absent — write to persistent volume, never to env file | `[claude-code]` | Eliminates manual key bootstrap step |
| F1-2 | Auto-generate `ENCRYPTION_KEY` as valid Fernet key (`base64.urlsafe_b64encode(secrets.token_bytes(32))`) at first boot | `[claude-code]` | Eliminates C10 — wrong format generated by deploy script |
| F1-3 | Run `alembic upgrade head` automatically at container start if not at head — log result, fail loudly if error | `[claude-code]` | Eliminates manual migration step |
| F1-4 | Bootstrap default workspace row if table is empty — org name from `FRONTEND_URL` domain, sane defaults | `[claude-code]` | Eliminates manual `PUT /workspace/brand` step after fresh deploy |
| ~~F1-5~~ | ~~First-boot validation check: on startup, verify all required env vars are set and correctly formatted — log a clear error and refuse to start if critical vars are missing or malformed~~ | done 2026-06-02 | Eliminates silent misconfiguration class (C10, C11) |
| F1-6 | Expose first-boot status in `GET /api/` health response: `{ "first_boot_complete": true/false, "migration_status": "head"/"pending", "env_valid": true/false }` | `[claude-code]` | Makes any org's deployment self-diagnosable without SSH |

## Priority 2b — Behavioral Parity (agents can verify staging matches localhost)

The missing feedback loop. `check-staging.sh` confirms the stack is alive — it says nothing about whether the feature works. Agents have no signal for behavioral divergence and report false success.

Parity has three layers. Code layer is solved (`git_sha`). State and behavior layers are not.

| # | Task | Owner | What it catches |
|---|---|---|---|
| P1 | `scripts/seed-staging-baseline.sh` — one command seeds staging with the same brands/docs/workspace as localhost after any recovery or fresh deploy | `[claude-code]` | C7 state drift — staging 0 brands, CMO returns "My Workspace" generics instead of brand-scoped output |
| P2 | `scripts/smoke-parity.sh workspace` — compare `GET /workspace`, `/brands`, `/providers` between localhost and staging; output PASS or FAIL with diff | `[claude-code]` | Immediate divergence signal after every deploy |
| P3 | `scripts/smoke-parity.sh cmo` — send test prompt to both envs, verify same module dispatched (not content) | `[claude-code]` | Feature-level parity for CMO dispatch |
| P4 | Health endpoint state readiness: add `workspace_configured`, `brands_count`, `providers_ready` to `GET /api/` | `[claude-code]` | Agent knows before testing whether env has testable state |
