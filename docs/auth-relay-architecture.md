# Auth Relay Architecture

> Status: BOS-side wiring complete (2026-05-25). Relay server not yet built. Build relay before first external client.
> Owner: Klaroha platform team.

---

## Problem

BOS is a self-hosted product. Every client deployment runs on its own domain
(`agency.com`, `brand.io`, `clientA.klaroha.com`). OAuth providers (Google,
Meta) require redirect URIs to be pre-registered in the developer console.
You cannot register a wildcard like `*.com`.

Without a relay, every new client domain requires a manual change to Klaroha's
Google Cloud Console and Meta Developer app — which breaks one-click deploy.

---

## Solution: Central Auth Relay

Klaroha runs a single lightweight service at `auth.klaroha.com`. All OAuth
callbacks from all Google and Meta flows across all client deployments land
here. The relay completes the token exchange (using Klaroha's client secrets,
which never ship in the Docker image), then hands the token back to the
originating client instance via an encrypted one-time token.

```
CLIENT INSTANCE (agency.com)          RELAY (auth.klaroha.com)        GOOGLE / META
        │                                       │                           │
        │── user clicks "Connect Drive" ──────► │                           │
        │   relay_url + instance_url in state   │                           │
        │                                       │── redirect to Google ────►│
        │                                       │   redirect_uri=           │
        │                                       │   auth.klaroha.com/...    │
        │                                       │                           │
        │                                       │◄── code ─────────────────│
        │                                       │── exchange code ─────────►│
        │                                       │◄── access_token ─────────│
        │                                       │                           │
        │                                       │  encrypt token → handoff  │
        │                                       │  store handoff (60s TTL)  │
        │◄── redirect to agency.com/social/     │                           │
        │    google-drive/callback              │                           │
        │    ?handoff_token=<one_time_token>    │                           │
        │                                       │                           │
        │── POST relay/claim ─────────────────►│                           │
        │   {handoff_token, relay_key}          │                           │
        │◄── {access_token, refresh_token,      │                           │
        │     expires_at, metadata} ────────────│                           │
        │                                       │                           │
        │  store in social_connections          │                           │
```

## What lives where

### `auth.klaroha.com` (relay server)

- Runs independently of any client instance
- Holds Klaroha's `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `META_APP_ID`,
  `META_APP_SECRET` — these never ship in Docker images
- Registered redirect URIs in Google Console:
  - `https://auth.klaroha.com/relay/google/callback`
  - `https://auth.klaroha.com/relay/meta/callback`
- Registered redirect URIs in Meta:
  - `https://auth.klaroha.com/relay/meta/callback`
- Stores handoff tokens in Redis with 60-second TTL (no persistent DB needed)
- Stateless otherwise

### Docker image (client deployment)

Ships with:
```
KLAROHA_RELAY_URL=https://auth.klaroha.com   # same in every image
KLAROHA_RELAY_KEY=<env-specific secret>       # set at deploy time, used to authenticate relay claims
```

Does NOT ship with:
- `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`
- `META_APP_ID` / `META_APP_SECRET`
- `GOOGLE_REDIRECT_URI` / `META_REDIRECT_URI`

Per-deployment operator config (the only things a deployer sets):
```
FRONTEND_URL=https://my-agency.com
DATABASE_URL=postgresql://...
API_SECRET_KEY=<random>
ENCRYPTION_KEY=<fernet key>
KLAROHA_RELAY_KEY=<shared with relay for this instance>
```

## Relay API

### `GET /relay/{platform}/start`

Called by BOS to begin an OAuth flow.

Query params:
- `instance_url` — the client's `FRONTEND_URL` (e.g. `https://agency.com`)
- `relay_key` — proves this is a registered BOS instance
- `platform` — `google_drive`, `gmail`, `google_calendar`, `youtube`, `facebook`
- `brand_id` — passed through, stored in state, returned in handoff
- `state` — PKCE state generated by BOS
- `verifier` — PKCE verifier (stored by relay, used in exchange)

Response: `{ authorize_url: "https://accounts.google.com/o/oauth2/v2/auth?..." }`

BOS redirects the browser to `authorize_url`.

---

### `GET /relay/{platform}/callback`

Registered with Google / Meta as the redirect URI. Receives the auth code.

1. Validates `state` matches a pending session
2. Exchanges code for tokens using Klaroha's client credentials
3. Fetches user metadata (email, page list for Meta, channel_id for YouTube)
4. Encrypts `{ access_token, refresh_token, expires_at, metadata, brand_id }` with a one-time key
5. Stores as `handoff:{uuid}` in Redis with 60-second TTL
6. Redirects browser to `{instance_url}/social/{platform}/callback?handoff_token={uuid}`

---

### `POST /relay/claim`

Called server-to-server by BOS after receiving a `handoff_token` in the browser callback.

Request:
```json
{
  "handoff_token": "uuid",
  "relay_key": "shared-secret"
}
```

Response:
```json
{
  "platform": "google_drive",
  "brand_id": "uuid",
  "access_token": "ya29...",
  "refresh_token": "1//...",
  "expires_at": "2026-06-24T12:00:00Z",
  "metadata": { "email": "user@example.com", "name": "..." }
}
```

- Token is deleted from Redis immediately after claim (one-time use)
- `relay_key` must match the registered key for the `instance_url` in the start session

BOS stores the token in `social_connections` exactly as it does today.

---

### `POST /relay/refresh`

Called server-to-server when a stored token needs refreshing (Google tokens expire after 1 hour).

Request:
```json
{
  "platform": "google_drive",
  "refresh_token": "<encrypted refresh token>",
  "relay_key": "shared-secret"
}
```

Response:
```json
{
  "access_token": "ya29...",
  "expires_at": "2026-06-24T13:00:00Z"
}
```

BOS's `get_page_token` calls this instead of refreshing directly with Google. This keeps the client_secret on the relay and avoids shipping it in the image.

## BOS-side wiring (complete as of 2026-05-25)

### `config.py`

Two optional settings added. Both default to empty string — empty = dev mode, no behaviour change.

```python
klaroha_relay_url: str = ""      # empty = dev mode (direct OAuth)
klaroha_relay_key: str = ""      # shared secret issued per-instance by relay onboarding script
```

`.env.example` documents both vars with setup instructions.

---

### `provider_auth.py`

`_google_redirect_uri()` is relay-aware. All four Google platforms share the single
registered relay URI; the relay redirects back to the platform-specific BOS callback
with a `handoff_token`.

```python
def _google_redirect_uri(platform: str, settings) -> str:
    if getattr(settings, "klaroha_relay_url", ""):
        relay = settings.klaroha_relay_url.rstrip("/")
        return f"{relay}/relay/google/callback"
    base = (settings.frontend_url or "http://localhost").rstrip("/")
    path = _GOOGLE_CALLBACK_PATHS.get(platform, f"/social/{platform}/callback")
    return f"{base}{path}"
```

Two relay helpers exported for use in `social.py`:

```python
GOOGLE_RELAY_PLATFORMS: frozenset[str]   # gmail, google_calendar, youtube, google_drive

async def relay_claim_handoff(handoff_token: str, settings) -> dict:
    """POST /relay/claim — one-time token exchange, returns access/refresh/metadata."""

async def relay_refresh_token(platform: str, refresh_token: str, settings) -> OAuthCredential:
    """POST /relay/refresh — delegate token refresh; refresh_token must be plaintext (decrypted)."""
```

---

### `routers/social.py`

All four Google callbacks (`/social/gmail/callback`, `/social/google-calendar/callback`,
`/social/youtube/callback`, `/social/google-drive/callback`) accept a `handoff_token`
query param. When present and `KLAROHA_RELAY_URL` is set, the callback claims the token
from the relay and stores the connection — the direct code-exchange path is skipped.

```python
# at the top of each Google callback:
if handoff_token and settings.klaroha_relay_url:
    payload = await relay_claim_handoff(handoff_token, settings)
    # build page dict from payload, call _store_connection() exactly as today
    ...
```

`get_page_token()` delegates refresh to the relay for Google platforms:

```python
if settings.klaroha_relay_url and platform in GOOGLE_RELAY_PLATFORMS:
    refreshed = await relay_refresh_token(platform, refresh_token, settings)
else:
    # direct refresh — dev mode / non-Google platforms unchanged
    ...
```

## What the relay still needs to implement (BOS is ready)

When the relay server is built, BOS requires no further changes for Google OAuth.
The relay must:

1. Accept `GET /relay/{platform}/start` — receive PKCE state + verifier from BOS, store
   them, build the Google authorize URL using Klaroha's `GOOGLE_CLIENT_SECRET`, return it.
2. Accept `GET /relay/google/callback` — validate state, exchange code with Google using
   the stored verifier, fetch user metadata, encrypt token + brand_id into a one-time
   handoff, store in Redis (60s TTL), redirect browser to
   `{instance_url}/social/{platform}/callback?handoff_token={uuid}`.
3. Accept `POST /relay/claim` — validate `relay_key`, return token payload, delete from Redis.
4. Accept `POST /relay/refresh` — receive plaintext `refresh_token`, call Google refresh
   with `GOOGLE_CLIENT_SECRET`, return new `access_token` + `expires_at`.

Note: `start_social_connect()` in BOS currently calls `handler.start_login()` directly,
which builds the Google authorize URL with `redirect_uri = {relay}/relay/google/callback`.
In relay mode the relay must also receive and store the PKCE verifier before the user
lands on Google — the relay start endpoint handles this. No BOS change is needed for
the callback or refresh paths; only the start flow requires the relay to be reachable
before `start_social_connect()` is called.

## Relay server implementation

Simple FastAPI app, ~300 lines. Separate repo: `klaroha/auth-relay`.

Dependencies: `fastapi`, `httpx`, `redis`, `cryptography` (already in BOS).

No database. Redis for handoff token TTL only. Stateless between requests.

Deployable to any VPS, Railway, Fly.io, etc. as a single container.

---

## Security properties

| Property | How |
|---|---|
| Client secrets never leave relay | Only relay calls Google/Meta token endpoints |
| Handoff tokens are one-time use | Deleted from Redis on first claim |
| Handoff tokens expire in 60s | Redis TTL — stale browser tabs can't be replayed |
| Instance authentication | `relay_key` shared secret per instance, set at deploy time |
| Token in transit | Relay → BOS over HTTPS only (server-to-server claim call) |
| Tokens at rest | BOS encrypts with `ENCRYPTION_KEY` via Fernet, as today |

## Dev mode (current state, no relay)

When `KLAROHA_RELAY_URL` is not set:

- `provider_auth.py` derives redirect URIs from `FRONTEND_URL` directly (already done)
- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` read from settings (already done)
- `META_APP_ID`, `META_APP_SECRET` stored in plugin vars via Admin → Plugins

This is acceptable for internal dev and for clients who bring their own OAuth apps
(advanced / enterprise self-host). The relay is required for one-click consumer deploy.
